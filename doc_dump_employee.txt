1. Session Overview
1.1 What we build: the productivity score predictor
A company wants to answer a simple question: what makes an employee more productive in a month? Is it years of experience? Training? Fewer tasks sent back for fixing? A new AI tool? Or does the size of the team matter? Everyone has an opinion, but opinions are not evidence. In this session we use data to find out.
We build a productivity score predictor. We give it seven facts about an employee-month (these are called features), and it predicts one number: the productivity score. The score is based on the number of tasks the person completed and got accepted in that month, and it can never go above 100. A person who completes 160 tasks or more in a month (full capacity) gets the maximum score of 100. Section 1.3 shows the exact calculation.
The tool has two jobs. Job 1 is to predict the score. Job 2 is more important: to tell us which features really affect the score, in which direction, and by how much. We build it in four steps:
Step 1: the simple guess. Predict the team average for everyone. We do this with NumPy, and it becomes our baseline (the score we must beat).
Step 2: one feature. Use linear regression with only experience and see how much it explains.
Step 3: all seven features together. See how much better the prediction becomes.
Step 4: which features matter? Rank the features, remove them one at a time, and check whether each effect is real or just luck. This is the main idea of the session.
Along the way, participants learn the most useful lesson of the session: a feature that looks important on its own may matter less when the others are included, and some features that sound important (like team size) may have no effect at all.
In simple words
A model is a rule that turns what we know (the features) into a guess about what we want to know (the productivity score). Regression is one way to find that rule from data. Linear means the rule is built by multiplying each feature by a number and adding everything up.
Read this first: the data is made up
The employee data in this guide is simulated. A small program (prepare_productivity_data.py) creates it, and it always creates the same numbers, so every facilitator sees the same results.
The patterns in it (more experience helps, rework and absence hurt, the AI assistant helps from month 13, team size does nothing) were put in on purpose. They are not facts about real employees.
Tell participants this at the very start. Never present these results as truth about real teams. Section 16 explains how to use your own data instead.
Use responsibly
The participants are employees themselves, so be careful with this topic. Present the predictor as a tool to understand what helps people do well (for example, to see that training or a good tool lifts the score, or to notice that someone needs support). It is not a tool to rank people or judge their performance. Module 12 has a short discussion on this.

1.3 How the productivity score is calculated
The score turns a count of tasks into a number from 0 to 100, so it is easy to read. The rule is:
productivity score = (tasks completed / 160) x 100, and never more than 100
Here 160 tasks in a month is called full capacity. It is a benchmark we chose, a little above the best month in the data. Reaching it earns the maximum score of 100.

1.5 What is covered
The session covers NumPy basics and the main ideas of linear regression. In plain terms, that means:
how a model is described (a straight line, and a line with more than one input);
how we measure mistakes (the loss function);
two ways to find the best line (a direct formula, and step-by-step improvement called gradient descent);
how to scale inputs, measure accuracy, and check that a model can be trusted;
how to find which features really affect the outcome (standardised weights, drop-one test and a luck check);
two common problems (a model that is too simple, and a model that is too complex), and a fix called ridge.
Other kinds of models (such as classification, trees and neural networks) are not covered.

4. Module 2: NumPy Arrays (15 min)
4.1 Why we use NumPy
A normal Python list can hold anything, but it is slow for maths because each item is stored separately. A NumPy array holds numbers of one type together in one block of memory, so it can do maths on millions of numbers very fast. Almost every data and AI library is built on NumPy.
In simple words
NumPy = a fast way to work with lots of numbers. We will use it for everything in this session.
import time
data = list(range(1_000_000))
arr = np.arange(1_000_000)
t = time.time(); [x * 2 for x in data]; print("list :", time.time() - t)
t = time.time(); arr * 2; print("numpy:", time.time() - t)

4.3 Picking items: indexing and slicing
Indexing means picking one item by its position. Slicing means picking a range. Positions start at 0, not 1.
exp6[0]        # 4   first record
exp6[-1]       # 5.3   last record
exp6[1:4]      # [3.4, 3, 4.1]   start inclusive, stop exclusive
exp6[::2]      # [4, 3, 2.9]   every second record
records[:, 0]  # all rows, column 0 (experience)
records[2, 1]  # row 2, column 1
records[1:3, :]# rows 1 and 2, all columns
Important: a slice is only a window onto the original data. It is not a separate copy. If you change the slice, the original changes too. Use .copy() when you want a separate copy.
s = exp6[:3]
s[0] = 999
print(exp6[0])        # 999  - the original changed
exp6[0] = 4         # restore it
safe = exp6[:3].copy()   # independent copy
4.4 Filtering with a boolean mask
A comparison such as exp6 > 3 gives a list of True and False values, one for each item. This list is called a boolean mask. If you use it to pick items, you keep only the True ones. This does the job of a for-loop with an if-statement, in one short line.
This matters a lot in our project. Some people's training hours were not recorded, so those cells are blank (NaN). A mask is how we skip them.
exp6 > 3                          # [True, True, False, True, False, True]
score6[exp6 > 3]                  # [56.9, 50.6, 65, 56.2]  scores of people with more than 3 years
good = (exp6 > 3) & (rework6 <= 3)   # use & | ~ with brackets
score6[good]                      # [56.9, 65]
np.where(score6 >= 60, "strong month", "weaker month")
 
values = np.array([88.0, np.nan, 91.0])   # NaN = a missing value
np.isnan(values)                  # [False  True False]
values[~np.isnan(values)]         # [88. 91.]  real numbers only
In simple words
A mask is a list of True and False. Put it inside the square brackets, and NumPy keeps only the items where it says True. The sign ~ means "not", so ~np.isnan(values) means "the ones that are not blank".

5. Module 3: Maths on Whole Arrays, Summaries and Broadcasting (12 min)
5.1 Doing maths on a whole array at once (vectorisation)
With NumPy you can do maths on a whole array in one line, with no loop. This is called vectorisation. Here is our simple guess ("predict the average score for everyone") worked out for all six records at once. The error of a guess is the real value minus the guess.
avg = score6.mean()            # 61.0  the average score of these six
guess = np.full(6, avg)        # the same guess for everyone
error = score6 - guess         # [-4.1, -10.4, 6.5, 4, 9, -4.8]
gap = 100 - score6             # [43.1, 49.4, 32.5, 35, 30, 43.8]  distance from the maximum score of 100
Ask the class: "What do you notice about the mistakes?" They are fairly big, and they go in both directions: one person is 10 points below the guess and another is 9 above. A guess that ignores everything about the person cannot do better.
Across all 5,838 records, this simple guess is wrong by about 9.1 points (RMSE, explained in Module 6). This is our baseline. Any model that cannot do better than this is not worth using. It is also a good moment to say: a small sample can fool you. Six rows told us very little about the whole file.
5.2 Summaries and the axis argument
score6.mean()      # average
score6.std()       # standard deviation: 6.9
score6.argmax()    # POSITION of the highest score: 4
np.median(score6)  # middle value: 60.95
np.cumsum(score6)  # running total
 
records.mean(axis=0)   # one value per COLUMN (down the rows)
records.mean(axis=1)   # one value per ROW (across the columns)
In simple words
The standard deviation tells you how spread out the numbers are. If it is small, most numbers sit close to the average. The median is the middle number once everything is sorted, so it is not pulled around by a few very big or very small values. argmax gives the position of the biggest value, not the value itself.
How to remember the axis: axis=0 squashes the rows (you get one answer per column). axis=1 squashes the columns (you get one answer per row).
5.3 Broadcasting
Broadcasting lets NumPy combine arrays of different shapes. The rule: compare the shapes from the right side. Two sizes fit together if they are equal, or if one of them is 1. A size of 1 gets stretched to match the other.
records - records.mean(axis=0)     # (3, 3) - (3,): subtract each column's mean
 
# Standardisation: needed later for gradient descent and for comparing features
z = (exp6 - exp6.mean()) / exp6.std()
Common error: trying to add shapes (3,) and (4,) fails, because 3 and 4 are not equal and neither is 1.
In simple words
Standardising means moving numbers so their average is 0 and their spread is 1. We do it by subtracting the mean and dividing by the standard deviation. After this, a value of +1 means "one standard deviation above average". Later, this lets us compare features that use very different units, such as years and tasks.
Choose-the-next-line poll (Module 3)

This is a quick tour of tools we will need soon. Go fast and let participants run the cells.

a.reshape(-1, 1)         # column vector; -1 means "work it out"
a.reshape(2, 3).T        # transpose -> shape (3, 2)
 
np.column_stack([exp6, rework6, absent6])   # features side by side, shape (6, 3)
 
A = np.array([[1, 2], [3, 4]])
v = np.array([5, 6])
A * A                    # element-wise product
A @ A                    # MATRIX product (rows times columns)
A @ v                    # matrix times vector -> [17 39]
np.linalg.solve(A, v)    # solves A x = v
 
rng = np.random.default_rng(42)   # seed makes results repeatable
rng.integers(20, 80, size=5)      # random integers from 20 to 79

Please stress two points:
The * sign multiplies item by item. The @ sign does matrix multiplication (each row of the first table is multiplied with each column of the second and added up). Regression needs the second.
The seed (the number 42) is the starting point of the random number generator. It makes random numbers repeat, so everyone gets the same "random" results.
In simple words
Reshape changes the layout of the same numbers without changing them. Transpose (.T) swaps rows and columns. A matrix is just a 2D array of numbers. column_stack puts several columns side by side to make a table of features.

7. Module 5: Regression Ideas (10 min)
7.1 The idea and the words
Imagine a chart. On the bottom axis (x) we put the years of experience. On the side axis (y) we put the productivity score. Each record is one dot. The dots slope upwards: more experience usually goes with a higher score.
Linear regression draws the straight line that passes as close as possible to all the dots. Then we use that line to predict.
The line is written as y = m x + c.
m is the slope. It says how many extra score points we get for each extra year of experience.
c is the intercept. It is where the line starts when x is 0. It is often just a starting number that makes the line fit.
When we have more than one feature, the model becomes y = c + w1 x1 + w2 x2 + .... Each w is a weight that says how much that feature matters: if the feature goes up by 1 and everything else stays the same, the prediction changes by w. It is called "linear" because the features are only multiplied by weights and added up.

7.2 The loss function: measuring how wrong the line is
For each record, the residual is the real value minus the predicted value. Some residuals are positive and some are negative, so if we just added them up, they would cancel out. To avoid this, we square each one (multiply it by itself) and then take the average:
MSE = average of (real - predicted) squared
MSE stands for mean squared error. Squaring does two things: it removes the minus signs, and it punishes big mistakes much more than small ones (a miss of 20 counts four times as much as a miss of 10). The line with the smallest MSE is called the least squares line. The function that measures how wrong we are is called the loss function.
In simple words
Think of MSE as a bowl. Every possible line is a point on the bowl, and the height is how wrong that line is. Training means finding the bottom of the bowl.
7.3 Two ways to reach the bottom of the bowl
The direct formula (normal equation). We use maths to jump straight to the bottom. For one feature: m = sum((x - mean_x)(y - mean_y)) / sum((x - mean_x)^2), and c = mean_y - m x mean_x. For many features: theta = inverse(X^T X) X^T y. (theta is just the name for the list of all learned numbers.)
Gradient descent. We start with a guess, check which way is downhill, take a small step that way, and repeat. The size of each step is the learning rate.
The direct formula is exact and quick for small problems. Gradient descent is used when the data is very large, or when no direct formula exists. That is why learners should know both.

9. Module 7: Gradient Descent and the Learning Rate (10 min)
Gradient descent finds the best line by taking small steps downhill. For each number we want to learn (the slope m and the intercept c), the gradient tells us: "if this number goes up a little, does the loss go up or down, and how fast?"
For one feature, the gradients are dm = 2 x mean(error x x) and dc = 2 x mean(error), where error = prediction - real. Then we move against the gradient (downhill): m = m - lr x dm. Here lr is the learning rate, the size of each step.
Before we start, we standardise x so that both numbers learn at a similar speed. This uses broadcasting from Module 3.
x_s = (x - x.mean()) / x.std()
m_s, c_s = 0.0, 0.0
lr = 0.1
for epoch in range(200):
    error = (m_s * x_s + c_s) - y
    dm = 2 * np.mean(error * x_s)
    dc = 2 * np.mean(error)
    m_s -= lr * dm
    c_s -= lr * dc
    if epoch % 50 == 0:
        print(epoch, np.mean(error ** 2).round(1))   # 3,975.7, then 63.9 ...
 
# convert back to the original units of x
m_gd = m_s / x.std()
c_gd = c_s - m_s * x.mean() / x.std()
print(m_gd.round(2), c_gd.round(1))   # 1.88 and 53.2: matches the closed form
In simple words
Gradient descent = guess, check which way is downhill, take a small step, repeat. After enough steps we reach the same answer as the direct formula. One epoch is one full pass over all the data. Convergence means the loss has stopped improving, so we have reached the bottom.

Answer and discussion: B. The gradient points uphill, so we go the opposite way. A climbs up the bowl and the loss grows. C throws away the old value. Run each option for a few rounds and watch the loss.

10. Module 8: All Seven Features Together (10 min)
10.1 The design matrix and the normal equation
So far we used one feature. But think about two people who both have 5 years of experience. One was never absent and had no rework. The other was absent 4 days and had 5 tasks sent back. Their scores will probably be very different. So it helps to use all seven features at once.
We put the features in a table called the design matrix X. Each row is one record. We add a first column of ones to carry the intercept. The numbers we learn are collected in a list called theta. Predictions are then simply X @ theta.

10.2 Gradient descent with more than one feature
The same step-by-step method works for any number of features. The gradient in matrix form is (2/n) X^T (X theta - y). The features must be standardised first.
mu, sd = F.mean(axis=0), F.std(axis=0)
Xs = np.column_stack([np.ones(len(y)), (F - mu) / sd])
theta_s = np.zeros(8)
for epoch in range(300):
    grad = (2 / len(y)) * Xs.T @ (Xs @ theta_s - y)
    theta_s -= 0.1 * grad
 
w = theta_s[1:] / sd                       # back to original units
b = theta_s[0] - np.sum(theta_s[1:] * mu / sd)
print(b.round(2), w.round(2))
# 66.98 and [1.87 0.56 -4.34 5.61 -1.41 -2.75 -0.03]: matches the normal equation
Two different methods, same result.
10.3 Why scaling matters
Gradient descent works faster and more safely when all features have a similar size. Here, team size is around 7.8 and ai_assistant is only 0 or 1, so they are very different in size.
The direct formula does not need scaling. But scaled weights are in "standard deviation" units, which lets you fairly compare which feature matters more. This is exactly what Module 9 uses.
Always work out the mean and standard deviation on the training data only, then reuse those same numbers on new data.

11. Module 9: Which Features Affect Productivity? (15 min)
This is the most important part of the session. In Module 8 we built a model that predicts well. Now we use it to answer the real question: which features affect the productivity score, and how much? We do it in four steps: rank the features fairly, remove them one at a time, check whether each effect is real or luck, and ask "what if" questions.
11.1 Why we cannot compare the raw weights
Look at the weights from Module 8. Experience has +1.87, AI assistant has +5.61, and task complexity has -4.34. Does that mean the AI assistant matters three times more than experience? No. The weights are in different units. One year of experience, one training hour, one complexity level and one yes/no switch are not the same size of change. Experience ranges from 0.5 to 14.4, while the AI assistant only goes from 0 to 1.
In simple words
To compare features fairly, we put them on the same scale first. We standardise each feature (average 0, spread 1) and then multiply each weight by that feature's standard deviation. The result is called a standardised weight. It answers: "if this feature goes up by one typical step (one standard deviation), how many score points change?" Now every feature uses the same kind of step, so we can compare them.

11.4 The luck check: is the effect real or just chance?
Even a useless feature will get a small weight, because real data is never perfectly tidy. How do we know whether a weight is real? We use the bootstrap: we re-draw the data at random many times (some rows picked twice, some not at all), refit the model each time, and see how much each weight shakes.
In simple words
The bootstrap is like asking: "If we had collected a slightly different group of employees, would we get the same answer?" If a weight stays on the same side of zero in almost every re-draw, the effect is steady and probably real. If it swings between positive and negative, it may be luck.

12.4 Features that are copies of each other (multicollinearity)
Multicollinearity means two or more features carry almost the same information. Then the model cannot decide how to share the credit between them, and the individual weights become unreliable. We measure it with the VIF (variance inflation factor). For each feature, we try to predict it from the other six. If that works very well, the feature is a near-copy and has a high VIF.
In simple words
VIF = 1 / (1 - R-squared), where the R-squared comes from predicting one feature using all the other features. A VIF of 1 means the feature is independent of the others. A rule of thumb says a value above 5 to 10 is a worry.
for j in range(7):
    others = [k for k in range(7) if k != j]
    Xo = np.column_stack([np.ones(len(y)), F[:, others]])
    t, *_ = np.linalg.lstsq(Xo, F[:, j], rcond=None)
    r = F[:, j] - Xo @ t
    r2_j = 1 - (r @ r) / np.sum((F[:, j] - F[:, j].mean()) ** 2)
    print(names[j], (1 / (1 - r2_j)).round(2))
All seven VIF values are between 1.00 and 1.27, far below 5. So our features do not copy each other, and the weights in Module 9 can be trusted. The largest are task_complexity (1.27), rework_tickets (1.26) and experience_years (1.23), because experienced people tend to get harder tasks and have less rework.

print(np.linalg.matrix_rank(X9), X9.shape[1])    # rank 8, but 9 columns
t9, *_ = np.linalg.lstsq(X9, y, rcond=None)
print(t9[1] + 12 * t9[8])                         # 1.87: only this combination is meaningful
The rank tells us how many columns carry independent information. Here it is 8, but there are 9 columns, so one is redundant. The solver can only fix the combination (years weight + 12 x months weight = 1.87, which is the same as the original 1.87), not the two weights separately. With np.linalg.solve you may get an error or huge numbers that cancel each other out. Either way, we cannot read meaning into the individual weights. Ways to fix it: remove one of the copies, combine them, collect more varied data, or use ridge (Module 11).

13. Module 11: Working on New Data (7 min)
13.1 A random split
We should judge a model on records it was not built on. A simple way: keep back 20 percent of the records at random and use them only for testing. The part used to build the model is the training set, and the part kept aside is the test set.
rng = np.random.default_rng(42)
idx = rng.permutation(len(y))
split = int(0.8 * len(y))
tr, te = idx[:split], idx[split:]
theta_tr, *_ = np.linalg.lstsq(X[tr], y[tr], rcond=None)
print(rmse(y[tr], X[tr] @ theta_tr).round(1))   # train: about 5.3
print(rmse(y[te], X[te] @ theta_tr).round(1))   # test : about 5.3
Train and test mistakes are almost the same. This is the healthy result for a simple model with plenty of data.
13.2 A split by time: the honest test for predicting the future
Our predictor will be used on future months. So we should test it that way: build it on the past and test it on the most recent months.
past, future = mo <= 18, mo >= 19     # 4,385 and 1,453 records
theta_t, *_ = np.linalg.lstsq(X[past], y[past], rcond=None)
pred_f = X[future] @ theta_t
print(rmse(y[future], pred_f).round(1))          # about 5.3
print(np.mean(y[future] - pred_f).round(2))      # about +0.48
print(rmse(y[future], np.full(future.sum(), y[past].mean())).round(1))   # baseline: 10.4
The model still beats the baseline by a wide margin (5.3 against 10.4). The test mistake is close to the training mistake of 5.3, so the model works well on new data. The small average error (+0.48) means the model guesses a little low for recent months.
In this data, the random split (5.3) and the time split (5.3) give similar answers, because the simulated process is steady. With real data that changes, for example after a reorganisation, the gap can be much bigger.
In simple words
Split the data the same way you will use the model. A random split quietly lets the model "peek" at the future.
13.3 Too simple and too complex (underfitting and overfitting)
Let us fit curves of different complexity using only 30 records (experience against score), and then test on the other records. A "degree 2" curve has a bend, a "degree 5" curve can wiggle a lot. These are still linear regression, because we just add features like x squared and x cubed.
rng2 = np.random.default_rng(5)
small = rng2.permutation(len(y))[:30]
rest = np.setdiff1d(np.arange(len(y)), small)
xz = (F[:, 0] - F[:, 0].mean()) / F[:, 0].std()
for d_ in [0, 1, 2, 5]:
    co = np.polyfit(xz[small], y[small], d_)
    print(d_, rmse(y[small], np.polyval(co, xz[small])).round(1),
             rmse(y[rest],  np.polyval(co, xz[rest])).round(1))

13.4 Ridge: keeping weights small
Ridge regression adds a penalty for big weights: loss = MSE + lambda x sum of squared weights. Lambda is the strength of the penalty. There is still a direct formula, a small change to the normal equation: theta = inverse(X^T X + lambda I) X^T y. The intercept is not penalised, and the features must be standardised.
A = np.column_stack([np.ones(len(y)), (F - mu) / sd])
np.set_printoptions(suppress=True)
for lam in [0, 1000, 10000]:
    Pm = lam * np.eye(8); Pm[0, 0] = 0          # intercept not penalised
    theta_r = np.linalg.solve(A.T @ A + Pm, A.T @ y)
    print(lam, theta_r.round(2))
# 0     : [62.39 4.35 1.67 -3.13 2.26 -2.31 -2.77 -0.07]
# 1000  : [62.39 3.6 1.44 -2.49 1.98 -2.32 -2.36 -0.05]
# 10000 : [62.39 1.54 0.65 -0.96 0.93 -1.39 -1.02 0.01]
The weights are now per standard deviation of each feature, in the order experience, training, complexity, AI, rework, absent days and team size. As lambda grows, every weight shrinks towards zero, and the weak ones (team size) stay near zero. Ridge is most useful when features copy each other, because then it shares the credit between them instead of letting one carry everything. We choose lambda by checking performance on data we kept aside. Lasso regression uses a different penalty and can push weights exactly to zero, which makes it a natural tool for finding unimportant features. Just mention its name.
Quiz 5
A model has RMSE 5 on training data and 25 on test data. What is the most likely problem?
A. Underfitting
B. Overfitting
C. The features are standardised
D. The learning rate is too small
Answer and discussion: B. Small mistakes on training data and much bigger mistakes on test data is the sign of overfitting.

One sentence to take home: experience alone explained about 23 percent of the ups and downs in the productivity score. All seven features together explained about 66 percent, but only six of them truly mattered. Team size added nothing, and the strongest effects were experience, absent days, task complexity, rework and the AI assistant. Data helped us separate what sounds important from what is important.
Two-minute talk: using a productivity analysis fairly
Ask the room: "If your manager had this analysis, what would be a good use and what would be a bad use?" Guide the answers towards these points:
Good uses: learning what helps people do well (training, tools, task planning), noticing early that a team needs support, and finding and removing blockers.
Bad uses: ranking people, deciding pay, or deciding who stays, based on a predicted score. The model only sees seven features. It does not see illness, family duties, team changes or personal strengths. A large part of the score (about one third) is still not explained.
Fairness: features such as absent days or rework may reflect someone's situation, not their effort. A model that learns from them can treat people unfairly. Check the mistakes for different groups before relying on a model, and always keep a human in the decision.
Openness: people who are measured by a model should know it exists, what it uses and how they can challenge it.
14.1 Common mistakes to warn about
Using Python's words and / or instead of & / | on arrays, and mixing up * with @.
Forgetting that a slice changes the original array.
Forgetting the column of ones for the intercept.
Not standardising before gradient descent, or working out the scaling on all the data instead of only the training data.
Using a learning rate that is too big and ignoring a loss that keeps rising.
Comparing raw weights across features with different units, instead of standardised weights.
Reading a small weight as "unimportant" without looking at the feature's scale, or reading a big weight as proof of cause.
Judging the model only on the data it was built on, or using a random split when the model will predict the future.
Forgetting to skip the blank (NaN) rows, which can make the whole calculation return NaN.
Predicting far outside the data the model has seen (this model has only seen 0.5 to 14.4 years of experience).
Forgetting the cap: a linear model does not know that scores stop at 100, so a prediction above 100 (possible for someone with every feature in their favour) should be read as 100.
Treating simulated results as facts about real employees, or using a prediction to judge individual people.
