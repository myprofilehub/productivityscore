NumPy Basics and Complete Linear Regression
Project: Does Predicting Later Improve the Projected T20 Score?
Two-hour session for corporate fresher employees: facilitator guide with live-demo code, polls, quizzes and assignments. All data is real: 3,280 men's T20 international first innings from Cricsheet, tested with a time-based split at 2024.
1. Session Overview
1.1 Running project: the T20 score projector
Every cricket broadcast shows a "projected score". The simplest version multiplies the current run rate by the overs remaining, but it ignores wickets lost and the fact that teams accelerate at the end. In this session participants build a better projector from real data and then use it to run a small, honest experiment. They first build the naive run-rate method with NumPy, then replace it with a linear regression fitted on 1,825 innings played up to 2023, and test it on 1,455 innings from 2024 to 2026 that the model never saw.
The project asks three questions. Each is phrased as a hypothesis that the data can confirm or reject:

Facilitator note: do not reveal the verdicts early
Before each experiment, ask participants to vote on the hypothesis. Most expect H2 and H3 to be true. The surprise is the lesson: a plausible idea has to earn its place by beating a baseline on data it was not fitted to.
How every experiment is judged:
Time-based split. Fit on innings from before 2024 (train), judge on innings from 2024 onward (test). A projector is used on future matches, so it is tested on future matches.
A baseline. The run-rate method (current runs divided by overs bowled, times 20) is the number to beat.
One metric in runs. Root mean squared error (RMSE) on the test set, reported with a bootstrap interval when two models are close.
An ablation rule. A feature that does not improve test accuracy is removed.

1.4 Scope
The session covers NumPy basics and the complete linear regression concept: the model, the loss function, the closed-form (normal equation) solution, gradient descent, multiple regression, feature scaling, evaluation metrics, model assumptions and diagnostics, multicollinearity, train/test evaluation with a time-based split, ablation tests (does a feature earn its place?), underfitting and overfitting, and ridge regularisation. Other model families (classification, trees, neural networks) are out of scope.

By the end of the session, participants will be able to:

Explain how a regression line is fitted by minimising mean squared error, and derive predictions from slope and intercept.
Implement simple and multiple linear regression from scratch with NumPy, using both the normal equation and gradient descent.

Explain why a time-based split copies how a forecasting model is used, and how ridge regularisation stabilises a model.

4. Module 2: NumPy Arrays (15 min)
4.1 Why NumPy
Python lists are flexible but slow for numerical work because every element is a separate Python object. A NumPy array stores numbers of one type in one block of memory and runs operations in compiled code. Almost every data and AI library is built on it.
import time
data = list(range(1_000_000))
arr = np.arange(1_000_000)
t = time.time(); [x * 2 for x in data]; print("list :", time.time() - t)
t = time.time(); arr * 2; print("numpy:", time.time() - t)

4.4 Boolean masking
A comparison on an array returns True and False values. Using that as an index keeps only the True positions. This replaces a for-loop containing an if-statement. The same idea will split the real data into train and test in Module 6.

final[runs10 > 70]                             # [214 179 133 209 201]
good_start = (runs10 > 70) & (wkts10 <= 2)     # use & | ~ with brackets
final[good_start]                              # [179 133 209 201]
np.where(final >= 180, "big total", "par or below")

5. Module 3: Vectorisation, Aggregation and Broadcasting (12 min)
5.1 Vectorised operations
Vectorisation means applying an operation to a whole array at once, with no explicit loop. Here is the naive projector from the opening question, for all six innings at once:
run_rate = runs10 / 10          # runs per over, every innings
naive = run_rate * 20           # run-rate projection
error = final - naive
print(naive)    # [178. 186. 176. 184. 108. 166.]
print(error)    # [ 36.  -7. -43.  25.  18.  35.]
Ask: "What do you notice about the errors?" Four of the six are positive: the run-rate method underestimates most of the time, because teams score faster in the second half. But not always: the third innings was 88 for 1 after 10 overs and still finished on 133, so the projection was 43 runs too high. Across all 3,280 innings the method underestimates 67 percent of the time, by 10.8 runs on average. A good model should learn the pattern from data and use wickets as well. This is the motivation for regression.
5.2 Aggregation and the axis argument
final.mean()               # 177.0   average final score
final.std()                # 35.4    standard deviation
final.argmax()             # 0       POSITION of the highest score
np.median(final)           # 190.0
np.cumsum(runs10)          # [ 89 182 270 362 416 499]   running total
matches.mean(axis=0)       # one value per COLUMN: [ 90.    2.33 175.33]
matches.mean(axis=1)       # one value per ROW:    [102.33  91.33  74.  ]
Memory aid: axis=0 collapses the rows, axis=1 collapses the columns.
5.3 Broadcasting
Broadcasting lets NumPy combine arrays of different shapes. Compare the shapes from the right-hand side; two dimensions are compatible when they are equal or one of them is 1. A dimension of size 1 is stretched to match.
matches - matches.mean(axis=0)     # (3, 3) - (3,): subtract each column's mean
# Standardisation: needed later for gradient descent
x_scaled = (runs10 - runs10.mean()) / runs10.std()
print(x_scaled.round(2))           # [ 0.43  0.73  0.36  0.66 -2.17 -0.01]
Common error: adding shapes (3,) and (4,) raises an error, because 3 and 4 are neither equal nor 1.

7. Module 5: Regression Concepts (11 min)
7.1 The idea and the vocabulary
Plot runs after 10 overs on the x-axis and the final score on the y-axis. The points trend upward. Linear regression finds the straight line that passes as close as possible to all points, and then uses that line to predict.
y = m x + c, where m is the slope (extra final runs for each extra run at the 10-over mark) and c is the intercept (the line's value at x = 0, often just a mathematical anchor). With several features the model is y = c + w1 x1 + w2 x2 + .... It is called linear because it is linear in the parameters.

7.2 The loss function
Residuals can be positive or negative and would cancel out, so we square them and take the average:
MSE = (1/n) x sum of (y_actual - y_predicted)^2
Squaring removes the sign and penalises large errors far more than small ones (a miss of 20 counts four times as much as a miss of 10). The line with the lowest MSE is the least squares line. Picture MSE as a bowl-shaped surface over all possible (m, c) pairs; training means finding the bottom of the bowl.
7.3 Two ways to reach the bottom
Closed form (normal equation): setting the slope of the bowl to zero gives direct formulas. For one feature: m = sum((x - mean_x)(y - mean_y)) / sum((x - mean_x)^2) and c = mean_y - m x mean_x. For many features: theta = inverse(X^T X) X^T y.
Gradient descent: start with a guess, work out which direction is downhill, take a small step, repeat. The step size is the learning rate.
The closed form is exact and quick for small problems. Gradient descent is used when the data is large or when the model has no closed form, which is why every learner should understand both.
7.4 Fit on the past, judge on the future
A model can always look good on the data it was fitted to. The honest question is how it does on innings it has never seen. Because a projector is used on future matches, we split by time: every innings played before 2024 is training data, and every innings from 2024 onward is test data. The test set is used only to report results, never to fit anything. This rule is used for every experiment in the session.

8.2 The baseline, then the fit
rmse = lambda a, b: np.sqrt(np.mean((a - b) ** 2))
naive = runs10 * 2                                # run-rate projection
print("Run-rate RMSE (test):", rmse(final[test], naive[test]).round(1))       # 24.7
print("Average error (test):", np.mean(final[test] - naive[test]).round(1))   # +8.8
print("Share underestimated:", np.mean(final[test] > naive[test]).round(2))   # 0.63
print("Predict-the-mean RMSE:", rmse(final[test], final[train].mean()).round(1))  # 44.7
x, y = runs10[train], final[train]                # fit on TRAIN only
m = ((x - x.mean()) * (y - y.mean())).sum() / ((x - x.mean()) ** 2).sum()
c = y.mean() - m * x.mean()
print(m.round(2), c.round(1))                     # 1.62 and 39.1
The run-rate method is wrong by about 25 runs typically, and on average 9 runs too low. That systematic error is exactly what regression can learn and correct. Predicting the average every time (44.7) is the weakest sensible baseline and shows how much information runs after 10 overs carry.
8.3 Evaluation metrics: train and test
def metrics(y, p):
    mse = np.mean((y - p) ** 2)
    rmse_ = np.sqrt(mse)                       # in runs; penalises big misses
    mae = np.mean(np.abs(y - p))               # in runs; average miss
    r2 = 1 - np.sum((y - p) ** 2) / np.sum((y - y.mean()) ** 2)
    return rmse_.round(1), mae.round(1), r2.round(3)
print(metrics(y, m * x + c))                                  # train: (22.1, 17.5, 0.651)
print(metrics(final[test], m * runs10[test] + c))             # test : (22.6, 17.9, 0.745)

9. Module 7: Gradient Descent and the Learning Rate (10 min)
For each parameter, the gradient tells us how the loss changes as that parameter increases. For MSE with one feature, dm = 2 x mean(error x x) and dc = 2 x mean(error), where error = prediction - actual. We then move against the gradient: m = m - lr x dm. Standardise x first so that both parameters learn at a similar speed (this reuses broadcasting). Training data only:
x_s = (x - x.mean()) / x.std()      # x, y are the TRAIN arrays from Module 6
m_s, c_s = 0.0, 0.0
lr = 0.1
for epoch in range(200):
    error = (m_s * x_s + c_s) - y
    dm = 2 * np.mean(error * x_s)
    dc = 2 * np.mean(error)
    m_s -= lr * dm
    c_s -= lr * dc
    if epoch % 50 == 0:
        print(epoch, np.mean(error ** 2).round(1))   # 24642.6, then 490.6 ...
# convert back to the original units of x
m_gd = m_s / x.std()
c_gd = c_s - m_s * x.mean() / x.std()
print(m_gd.round(2), c_gd.round(1))   # 1.62 and 39.1: matches the closed form
Choose-the-next-line poll (Module 7)
Inside the loop, how should the parameter be updated?
      A. m_s += lr * dm
      B. m_s -= lr * dm
      C. m_s = dm
Answer and discussion: B. The gradient points uphill, so we move against it. A climbs the bowl and the loss grows; C throws away the old value. Run each option for a few epochs and watch the printed loss.
9.1 The learning rate experiment
Rerun the loop with three values and ask participants to predict each outcome by poll before running. The best possible training MSE is about 490.6 (RMSE 22.1).

10. Module 8: Multiple Regression (11 min)
10.1 Design matrix and normal equation
A team that is 80 for 1 is in a better position than one that is 80 for 5. Every innings becomes a row of the design matrix X, with a leading column of ones for the intercept. The parameters form a vector theta, and predictions are simply X @ theta. The parameters are fitted on the training rows only.
X = np.column_stack([np.ones(n), runs10, wkts10])        # shape (3280, 3)
Xtr, ytr = X[train], final[train]
theta = np.linalg.solve(Xtr.T @ Xtr, Xtr.T @ ytr)        # normal equation
theta2, *_ = np.linalg.lstsq(Xtr, ytr, rcond=None)       # same, numerically safer
print(theta.round(2))                                    # [62.3   1.45 -4.52]
pred = X @ theta                                         # predictions for every innings
k = 2                                                    # number of features
r2 = 1 - np.sum((ytr - pred[train]) ** 2) / np.sum((ytr - ytr.mean()) ** 2)
adj_r2 = 1 - (1 - r2) * (len(ytr) - 1) / (len(ytr) - k - 1)
print(rmse(ytr, pred[train]).round(1), r2.round(3), adj_r2.round(3))   # 21.5 0.673 0.672
print(rmse(final[test], pred[test]).round(1))                          # 22.1 (test)
print((theta @ np.array([1, 80, 2])).round(1))                         # 80 for 2: 169.6
Interpret the weights in plain language: holding wickets fixed, each extra run at 10 overs adds about 1.45 to the final score; holding runs fixed, each wicket lost reduces it by about 4.5. Notice that the runs weight is smaller than the 1.62 of the simple model. Teams with more runs have usually lost fewer wickets, so the simple slope was also picking up part of the wicket effect. This is what "holding the other features fixed" means. Test RMSE improves from 22.6 to 22.1: a real but modest gain, because a T20 innings stays uncertain whatever features we use. Adjusted R-squared corrects R-squared for the number of features: plain R-squared never decreases when a feature is added, even a useless one, but adjusted R-squared can.
10.2 Gradient descent in matrix form
The same loop works for any number of features in three lines, because the gradient of MSE is (2/n) X^T (X theta - y). Features must be standardised, using the training mean and standard deviation.
F = np.column_stack([runs10, wkts10])[train]
mu, sd = F.mean(axis=0), F.std(axis=0)
Xs = np.column_stack([np.ones(len(F)), (F - mu) / sd])
theta_s = np.zeros(3)
for epoch in range(300):
    grad = (2 / len(F)) * Xs.T @ (Xs @ theta_s - ytr)
    theta_s -= 0.1 * grad
w = theta_s[1:] / sd                                  # back to original units
b = theta_s[0] - np.sum(theta_s[1:] * mu / sd)
print(b.round(2), w.round(2))                         # 62.3 and [ 1.45 -4.52]: matches
10.3 Why scaling matters
Gradient descent converges faster and more reliably when features share a similar scale (runs are around 71, wickets around 2.6).
The normal equation does not need scaling, but scaled coefficients are in standard-deviation units and allow a fair comparison of feature importance.
Always compute the mean and standard deviation on the training data only, then reuse them on new data.

12.1 H2: does predicting stage by stage help?
The idea sounds sensible: instead of jumping from over 6 to the final total, predict the state at over 10 (runs and wickets), then predict over 15 from that, and only then predict the final. Each step looks easier. Ask for a vote first:
Poll (Module 10)
Starting from over 6, the chained (stage by stage) projector's test RMSE compared with the direct model's will be:
      A. Clearly better (more than 1 run lower)
      B. The same, within a fraction of a run
      C. Clearly worse (more than 1 run higher)
Answer and discussion: B. They differ by less than 0.1 run. The explanation follows the results.
Each stage model is fitted on training innings, using the true state at the current checkpoint to predict the next one. On the test set the predicted state is then fed forward, so errors can compound. Before running, define the bootstrap helper that tells us whether a difference between two models is real or noise:
def boot_diff(err_a, err_b, B=2000, seed=0):
    """95 percent interval for RMSE(a) - RMSE(b) over resampled test innings."""
    rng = np.random.default_rng(seed)
    idx = rng.integers(0, len(err_a), size=(B, len(err_a)))   # B resamples
    d = np.sqrt((err_a[idx] ** 2).mean(axis=1)) - np.sqrt((err_b[idx] ** 2).mean(axis=1))
    return np.percentile(d, [2.5, 97.5]).round(2)
def chained(path):
    """Predict (runs, wickets) at each next checkpoint, then the final total."""
    S = state(path[0])[test]
    for a, b in zip(path[:-1], path[1:]):
        th_r = fit(state(a)[train], runs[b][train])
        th_w = fit(state(a)[train], wkts[b][train])
        S = np.column_stack([predict(th_r, S), predict(th_w, S)])
    th_f = fit(state(path[-1])[train], final[train])
    return predict(th_f, S)
for path in [[6, 10], [6, 10, 15], [6, 10, 12, 15, 18], [10, 15], [10, 12, 15, 18]]:
    ch, dr = chained(path), direct[path[0]]
    print(path, rmse(ft, ch).round(2), rmse(ft, dr).round(2),
          boot_diff(ft - ch, ft - dr))

The training RMSE shows the ceiling: from over 6, chained 26.98 against direct 26.94; from over 10 through 12, 15 and 18, chained 21.54 against direct 21.46. 13.4 Multicollinearity (cut-able)
Powerplay runs (the first 6 overs) are part of the runs after 10 overs, so the two features are strongly related. Check how strongly, and what happens when both are used (training innings):
a, b, c3 = runs10[train], runs6[train], wkts10[train]
r = np.corrcoef(a, b)[0, 1]
print(r.round(3), (1 / (1 - r ** 2)).round(1))              # 0.889 and 4.8 (the VIF)
X3 = np.column_stack([np.ones(len(a)), a, b, c3])
print(np.linalg.lstsq(X3, ytr, rcond=None)[0].round(2))     # [60.38  1.67 -0.32 -4.21]
The variance inflation factor (VIF) is 1 / (1 - r squared) for a pair of features; a common rule of thumb treats values above 5 to 10 as a concern. Here it is about 4.8, which is moderate: the powerplay runs add almost nothing (weight -0.32; training R-squared moves only from 0.673 to 0.675) because runs10 already contains that information. Now the extreme case: add a feature that is exactly a combination of the others, runs in overs 7 to 10 (runs10 - runs6).
X4 = np.column_stack([np.ones(len(a)), b, a, a - b, c3])
print(np.linalg.matrix_rank(X4), X4.shape[1])                # 4 but 5 columns
print(np.linalg.solve(X4.T @ X4, X4.T @ ytr).round(2))       # one set of weights
print(np.linalg.lstsq(X4, ytr, rcond=None)[0].round(2))      # a different set
# about [60.38  2.34 -0.99  2.66 -4.21] and [60.38  0.34  1.    0.66 -4.21]
The rank shows that one column is redundant. Both weight sets give identical predictions, yet the individual weights disagree wildly, so they cannot be interpreted. (On some computers np.linalg.solve raises an error instead of returning numbers; your results may differ slightly.) Remedies: drop one of the redundant features, combine them, collect more varied data, or use ridge regularisation.

13.6 Ridge regularisation (cut-able)
Ridge regression adds a penalty on the size of the weights: loss = MSE + lambda x sum of squared weights. It has a closed form that is a small change to the normal equation: theta = inverse(X^T X + lambda I) X^T y, leaving the intercept unpenalised. Features must be standardised.
Z = np.column_stack([runs10, runs6, wkts10])
zm, zs = Z[train].mean(axis=0), Z[train].std(axis=0)         # from TRAIN only
A = np.column_stack([np.ones(n), (Z - zm) / zs])
for lam in [0, 100, 1000]:
    P = lam * np.eye(4); P[0, 0] = 0                         # do not penalise the intercept
    th = np.linalg.solve(A[train].T @ A[train] + P, A[train].T @ final[train])
    print(lam, th.round(2), rmse(final[test], A[test] @ th).round(2))
# 0   : [152.43  31.13  -4.21  -5.86]  test 21.94
# 100 : [152.43  24.32   1.42  -6.8 ]  test 22.45
# 1000: [152.43  13.15   7.39  -6.8 ]  test 25.35
Weights are now per standard deviation of each feature. As lambda grows, the weights shrink and the two related features (runs10 and runs6) share the credit instead of one cancelling the other. But look at the test column: accuracy gets worse as lambda grows. With 1,825 innings and three features the plain model is already stable, so ridge is not needed here. Its value appears when there are many columns or near-duplicates, as with the 34 venue columns in Module 10, where lambda 50 pulled the test error back from 22.46 to 22.15. Lambda is chosen by checking performance on held-back data. Lasso regression uses an absolute-value penalty and can drive weights exactly to zero; mention it by name only.

14.1 Common mistakes to warn about
Using Python and / or instead of & / | on arrays, and confusing * with @.
Forgetting that slices change the original array.
Forgetting the column of ones for the intercept.
Not standardising before gradient descent, or computing the scaling on all data instead of the training data only.
A learning rate that is too large while ignoring a rising loss.
Fitting on the test set, or choosing features by repeatedly looking at test results. Keep a validation window for decisions and use the test set once.
Comparing R-squared across different data sets instead of RMSE.
Reading a small difference between two models as a real improvement without checking its interval.
Extrapolating far outside the data (the model has only seen 12 to 171 runs after 10 overs and 8 to 113 after 6).
Reading regression coefficients as proof of cause: they describe association in the data.
14.2 Limits of this study to state honestly
The data are T20 internationals only, first innings only. Chasing innings, other leagues and shortened matches are not covered.
Innings that ended all out before 15 overs (66, about 2 percent) are excluded so that all checkpoints share the same rows.
The test period runs from January 2024 to mid-September 2026. Results will move slightly when the data is refreshed.
The venue conclusion applies to T20 internationals, where venues rarely repeat. It was confirmed on a validation window, but it is not a statement about leagues with a few fixed home grounds.
Only linear models of runs and wickets were tested. Team strength, pitch, weather and the match situation are not in the data.

Scenario. A broadcaster wants an early-warning projection after only 6 overs and asks how much better it becomes with every over that is bowled. Build the projector and judge it honestly, fitting on innings before 2024 and testing on innings from 2024 onward throughout.
Write reusable functions fit_line(x, y), predict(x, m, c) and metrics(y, y_pred) returning MSE, RMSE, MAE and R-squared. Fit final on runs6 and compare it with the run-rate method (runs6 x 20 / 6) on the test set.
Solve the same problem with gradient descent on standardised x, and show it reaches the same slope and intercept. Try two learning rates and describe what happens.
Add wkts6 as a second feature. Solve with both the normal equation and lstsq, and report R-squared and adjusted R-squared.
Repeat the two-feature model at overs 6, 10, 12, 15 and 18. Report test RMSE for each, draw the error against the over, and say by how much the error falls between over 6 and over 15.
Add runs10 and wkts10 to the over-6 features (four features). How much does knowing four more overs add? Compare adjusted R-squared across the three models, and check the correlation between runs6 and runs10.
Build the chained projector 6 to 10 to 15 to final. Compare it with the direct over-6 model using the bootstrap interval, and explain in three sentences why there is no gain.
Test venue features at over 6 and over 15: one-hot venues (at least 15 training innings) with plain least squares and with ridge for two values of lambda. Decide whether to keep them. Stretch: build the venue-average feature, leaving each training innings out of its own venue's average, and test it.
